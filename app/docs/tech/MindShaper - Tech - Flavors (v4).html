Tech: applicationId i flavory

Jak dwie instancje aplikacji — standard i sandbox — instalują się obok siebie z osobnymi danymi. Dokument opisuje rzeczy zaimplementowane.

applicationId

  • Trzy człony, stała kolejność — base → flavor → buildType. Odwrócenie wymagałoby ręcznego applicationId w bloku.
  • namespace ≠ applicationId — dwie role, u nas przypadkiem ta sama wartość.
    • namespace — pakiet wygenerowanego R/BuildConfig, rzecz kompilacji; nie zmienia się per wariant
    • applicationId — tożsamość aplikacji na urządzeniu i w Google Play; to ona decyduje o współistnieniu

Flavory — dlaczego dwa

  • Wymiar wymaga flavora. flavorDimensions bez żadnego productFlavor = błąd konfiguracji; każdy flavor musi mieć dimension, nawet przy jednym wymiarze.
  • standard celowo pusty. Bez suffixu bazowe id zostaje nietknięte → zgodność wstecz z już zainstalowaną aplikacją.
  • sandbox = jedyna różnica — applicationIdSuffix = ".sandbox", reszta dziedziczona.

Instalacja obok siebie

  • Różne id = różne pakiety. Android traktuje je jako osobne aplikacje.
  • Izolowane dane. Każda instancja ma własne pliki i własną bazę Room — myśli i tagi się nie współdzielą; sandbox startuje z pustą bazą.
  • Podpis kluczem debug. Gradle podpisuje debug automatycznie → zero keystore. Release wymagałby własnego keystore, dlatego druga instancja to build debug.
  • versionNameSuffix niezależny od id — debug dokłada -DEBUG do versionName, bez wpływu na applicationId.
  • Zmiana applicationId po publikacji = nowa aplikacja w Play — dlatego standardRelease zostaje bez suffixów.

Zasoby flavora

  • src/sandbox/ nadpisuje src/main/ — Gradle scala zasoby, folder flavora ma wyższy priorytet.
  • app_name — ten sam klucz w src/sandbox/res/values/strings.xml przykrywa wartość z main tylko dla wariantów sandbox*: „MindShaper” / „MindShaper SB”.
    • to override, nie drugi wpis → brak błędu „duplicate resources”
    • tą samą drogą można podmienić ikonę (mipmap-*), kolory itd., bez ruszania main
  • fileprovider bez kolizji. ${applicationId}.fileprovider rozwija się per wariant. Authority jest globalnie unikalne w systemie — dwie aplikacje z tym samym = konflikt przy instalacji.

Backup — izolacja per flavor

  • Problem. Backup ląduje we wspólnym Downloads/mindshaper_backup/; przy stałej nazwie pliku dwie instancje nadpisywałyby sobie snapshoty, a restore ciągnąłby cudze dane.
  • Sufiks na folderze, nie na nazwie pliku. Jedno miejsce — getBackupDirectory() — przez które idą createSnapshot, restoreSnapshot i getSnapshotStats.
    • izolacja spójna dla zapisu, listy i odczytu; każda instancja widzi tylko swój folder
    • nazwa pliku zostaje prosta: mindshaper_v{ver}_{data}.json
  • standard na starym folderze. Warunek flavor.isNotBlank() && flavor != "standard" → _$flavor.
    • standard → mindshaper_backup/ — widzi stare backupy, zero migracji
    • sandbox → mindshaper_backup_sandbox/
  • Bez dodatkowej roboty — createSnapshot woła backupDir.mkdirs(), a getSnapshotStats ma ?: emptyArray(), więc brak folderu nie wywala listy.

Taski testów

  • assemble<Wariant> zależy od testów swojego wariantu. Flavory rozbiły testDebugUnitTest na testStandardDebugUnitTest / testSandboxDebugUnitTest, więc nazwa taska jest liczona z wariantu: "test${name.removePrefix("assemble")}UnitTest".
  • Leniwe API. tasks.matching { … }.configureEach { … } i zależność przez tasks.matching { it.name == unitTestTask }:
    • task assemble bez pasującego taska testów (np. assemble<Wariant>UnitTest/AndroidTest) nie dostaje zależności zamiast błędu „Task not found”
    • brak whenTaskAdded + dependsOn("string") — to API dawało ostrzeżenie o niezgodności z Gradle 9.0
  • Jeden wspólny zestaw testów — gdyby był potrzebny, wiązać na stałe do testStandardDebugUnitTest.

Nazwy plików APK

  • MindShaper-${name}-v${versionCode}-${date}.apk — name = pełna nazwa wariantu (np. sandboxDebug), więc warianty nie nadpisują sobie APK.

Pułapki — nie ruszać

  • Magiczny string "standard" w getBackupDirectory(). Przemianowanie flavora standard „zgubi” stare backupy — dostanie folder z sufiksem.
  • Hardkodowane authority w manifeście zamiast ${applicationId} — dwie instancje przestaną się instalować obok siebie.

Implementacja

  • app/build.gradle.kts — flavory, suffixy, nazwy APK, taski testów
  • src/sandbox/res/values/strings.xml — app_name
