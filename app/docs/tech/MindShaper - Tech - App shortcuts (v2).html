Tech: Skróty aplikacji

Jak działają skróty widoczne po przytrzymaniu ikony aplikacji. Dokument opisuje rzeczy zaimplementowane. Jakie skróty są, ustala dokument wymagań (Skróty aplikacji).

Mechanizm

  • Skrót = intencja z parametrem, nie osobna ścieżka. Skróty „Złap…” otwierają to samo CaptureActivity i różnią się tylko extra EXTRA_CAPTURE_FORM z nazwą wartości DefaultCaptureForm. Otwieranie formy ma jedną implementację, w autoOpenDefaultFormIfNeeded().
  • Nadpisanie, nie rozgałęzienie. autoOpenDefaultFormIfNeeded() używa extra zamiast ustawienia. Brak extra = forma z AppSettingsStorage.getDefaultCaptureForm().
  • Odporność na złą wartość. runCatching { DefaultCaptureForm.valueOf(name) }.getOrNull() — nieznana wartość cicho spada do ustawienia domyślnego zamiast rzucić IllegalArgumentException.
  • „Twórz fiszki” — ten sam wzorzec. FlashcardsActivity z extra EXTRA_NEW_SET otwiera dialog nowego zestawu, openNewSet(), wspólny z FAB „+”.
    • tylko przy pierwszym utworzeniu (savedInstanceState == null) — obrót nie otwiera dialogu ponownie, jak EXTRA_START_SESSION z przypomnienia

Rejestracja

  • Dynamiczne, nie res/xml/shortcuts.xml. Statyczny XML nie rozwija ${applicationId}, więc gubi wariant .debug.
  • AppShortcuts.register() (singleton Hilt) — wołane przy starcie aplikacji (ApplicationMain) i przy przełączeniu fiszek w Ustawieniach. Zestaw zależy od ustawień: fiszki wyłączone = brak skrótu „Twórz fiszki”.
  • setDynamicShortcuts(list), nie pushDynamicShortcut. Podmienia cały zestaw:
    • kolejność zawsze z listy: Twórz fiszki, Złap notatkę, Złap głosówkę, Złap zdjęcie
    • skrót pominięty na liście znika z launchera — wyłączone fiszki, dawny new_thought ze starszych buildów; push zostawiłby go na stałe
  • Fabryka buildShortcut(id, labelRes, iconRes, targetIntent). Pozycje różnią się tylko danymi, więc jeden builder; buildCaptureShortcut dokłada do niej extra formy.
  • @StringRes / @DrawableRes na parametrach — Lint pilnuje, by nie wpadł tam dowolny Int.

Stos intencji

  • setIntents(arrayOf(homeIntent, targetIntent)) — Home pierwszy, cel ostatni. Launcher układa wcześniejsze intencje pod ostatnią, więc BACK z zimnego startu ląduje na HomeActivity zamiast wyrzucać z aplikacji.
  • Intent Home bez CATEGORY_LAUNCHER. Home pod spodem nie przekierowuje na ekran startowy (Tech — Ekran startowy).

Etykiety i ikony

  • Jeden string na skrót. shortLabel i longLabel dostają tę samą wartość — API wymaga obu, a przy krótkich etykietach dłuższy wariant nic nie wnosi.
  • Vectory ic_shortcut_new_flashcards / _text / _voice / _photo. Pomarańczowy dysk (#FFA86B) + biały glif w <group> ze skalą 0.58.
    • glify reużyte z ic_activity_flashcards / ic_thought_type_rich_text / _recording / _photo (ten sam viewport 960) — brak nowych ścieżek do utrzymania
  • Kolor wpisany wprost, nie ?attr/.... Launcher renderuje ikony skrótów we własnym motywie, gdzie atrybuty motywu rozwiązują się nieprzewidywalnie.

Wyłączone funkcje

  • Fiszki — skrótu nie ma na liście (patrz Rejestracja).
  • Głosówka / zdjęcie — skrót zostaje. autoOpenVoiceRecording() / autoOpenPhoto() sprawdzają isVoiceRecordingEnabled() / isPhotoFeatureEnabled() i pokazują dialog zachęty — ta sama ścieżka co z aplikacji, bez dodatkowego kodu.

Implementacja

  • services/AppShortcuts.kt — lista skrótów, rejestracja
  • ApplicationMain.kt — start aplikacji
  • activities/settings/SettingsActivity.kt — przełącznik fiszek
  • activities/capture/CaptureActivity.kt — EXTRA_CAPTURE_FORM
  • activities/flashcards/FlashcardsActivity.kt — EXTRA_NEW_SET

Do weryfikacji na urządzeniu

  • kolejność skrótów w launcherze (część nakładek producenckich ma własne zdanie)
  • czytelność glifów w małym rozmiarze ikony skrótu
  • skrót do wyłączonej głosówki / zdjęcia → dialog zachęty przy zimnym starcie
  • „Twórz fiszki”: dialog nowego zestawu od razu po starcie; „Zakończ” → zestaw, BACK → lista fiszek → Home
  • wyłączenie fiszek w Ustawieniach → skrót znika, włączenie → wraca na pierwszą pozycję
